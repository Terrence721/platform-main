# Architecture Decisions

Last updated: August 8, 2026

This document records the architectural decisions made in this repo that deviate from the real ngrx/platform source — not a general description of how NgRx works. For what was added verbatim vs. redesigned, and why, see the [README](../README.md#-why-this-matters). For the phase-by-phase build log, see [todo.md](../todo.md).

## Composition over inheritance: `Store`, `ActionsSubject`, `ReducerManager`, `State`, `ScannedActionsSubject`

**Status:** Done — [`7ae7781`](https://github.com/Terrence721/platform-main/commit/7ae7781) (`ActionsSubject`), [`7ae7781`](https://github.com/Terrence721/platform-main/commit/7ae7781) (`ReducerManager`), [`7ae7781`](https://github.com/Terrence721/platform-main/commit/7ae7781) (`Store`), [`bb005ff`](https://github.com/Terrence721/platform-main/commit/bb005ff) (`State`/`StateObservable`, `MockState`, `MockReducerManager`), [`0998b87`](https://github.com/Terrence721/platform-main/commit/0998b87) (`ScannedActionsSubject`). Confirmed via a full-module audit — every `extends` in every `.ts` file under `modules/store`, not a spot-check — that no other production class in the module extends an RxJS type.

### Context

The real ngrx/platform `Store`, `ActionsSubject`, and `ReducerManager` extend RxJS's `Observable`/`BehaviorSubject`/`Subject` types directly:

```ts
export class Store<T = object> extends Observable<T> implements Observer<Action> { ... }
export class ActionsSubject extends BehaviorSubject<Action> implements OnDestroy { ... }
export class ReducerManager extends BehaviorSubject<ActionReducer<any, any>> implements OnDestroy { ... }
```

Each of these classes has a narrow, specific job — `Store` dispatches actions and exposes selectable state; `ActionsSubject` is an internal action bus; `ReducerManager` tracks the combined reducer and reacts to feature (un)registration. Extending an RxJS type hands the class the _entire_ Observable/Subject operator surface as a side effect of inheritance — `pipe`, `lift`, `toPromise`, `forEach`, `asObservable`, and everything else — regardless of whether that surface is part of the class's actual contract. `Store` even had to override `lift()` for no functional reason of its own: RxJS's internal operator-chaining machinery calls `lift()` on the source object when you `.pipe()` a subclassed Observable, and without the override it would silently hand back a plain `Observable` instead of a `Store`, breaking every subsequent method call in the chain. That override existing at all is a symptom of the design, not a feature of it.

### Decision

Each of the three classes now **composes** an RxJS subject internally — holds it as a private field — instead of extending one:

- `ActionsSubject` holds a private `BehaviorSubject<Action>`. Its public surface is hand-picked to match what an action bus actually needs: `next()` (with the same runtime validation as before), `subscribe()`, `error()`, `complete()`, `asObservable()`, `ngOnDestroy()`. No `pipe`, no `lift`, not an `instanceof Observable`.
- `ReducerManager` holds a private `BehaviorSubject<ActionReducer>`, exposed via a new `asObservable()` method. The codebase already had a separate `ReducerObservable` DI token for consumers that need the Observable view (used by `state.ts`, `store_module.ts`, `provide_store.ts`) — its provider wiring changed from `{ provide: ReducerObservable, useExisting: ReducerManager }` to a factory calling `.asObservable()`, so none of those three consumers needed to change at all.
- `Store` holds the injected `StateObservable` as a private field, exposed publicly as `state$: Observable<T>`. `select()` keeps its full overload set (including the deprecated props-based variants) and now derives from `state$` instead of `this`. `selectSignal()` is unaffected — it never depended on Store being an Observable.

Unlike the other two, the `Store` change **removes capability**, not just relocates it: `Store` no longer implements RxJS's `Observer<Action>` interface, so `next()`, `error()`, `complete()`, `subscribe()`, and `pipe()` are gone from its public surface entirely. A caller that wants the raw state stream uses `store.state$` directly; there is no equivalent for "pass `store` itself to `.subscribe()` as a dispatch sink," a capability the real ngrx `Store` has purely as a side effect of extending `Observable`/implementing `Observer`, not as a documented, load-bearing feature.

A second pass caught two classes the first pass missed: `State` (the internal service that reduces actions into the current state tree) extended `BehaviorSubject<any>` directly, and its DI-token abstract class `StateObservable` extended `Observable<any>` on top of an already-abstract `state: Signal<any>` member. Same fix, same reasoning: `State` now composes a private `BehaviorSubject`, exposing `state$: Observable<any>`, `state: Signal<T>`, and a `value` getter (the one piece of `BehaviorSubject`'s surface actually read synchronously, by `integration.spec.ts`/`integration_signals.spec.ts`) — nothing else. `StateObservable` changes from `extends Observable<any>` to a plain abstract class carrying `state$`/`state`, so `Store`'s constructor now reads `state.state$`/`state.state` off the injected token instead of treating the token itself as an `Observable`. The testing package's `MockState` and `MockReducerManager` got the identical treatment, since they exist specifically to stand in for `State`/`ReducerManager` and inheriting `BehaviorSubject` directly would leave them on the old design after the real classes moved off it.

**`ReducerObservable` was deliberately left as `extends Observable<ActionReducer>`**, unlike `StateObservable`. The distinction: `ReducerObservable` carries zero members of its own — it's a pure type-level anchor Angular's DI needs (a class reference, since TypeScript interfaces don't exist at runtime) for "give me the Observable view of the reducer." Nothing about it bundles unrelated behavior the way `Store`/`ActionsSubject`/`ReducerManager`/`State` did, where a service class's own methods sat awkwardly next to an inherited Subject surface. `StateObservable` was different specifically because it wasn't a pure marker — it bundled `Observable` inheritance with its own abstract `state: Signal<any>` member, the same "two unrelated contracts glued together via `extends`" shape as the classes fixed in the first pass. Treating these two DI tokens differently isn't inconsistency; it's the same rule applied to two cases that aren't actually alike.

A third pass — this time a deliberate full-module audit (`grep extends` across every `.ts` file in `modules/store`: `src`, `testing/src`, `schematics-core`, `schematics`, `migrations`, not a spot-check of the classes already suspected) — caught one more: `ScannedActionsSubject extends Subject<Action> implements OnDestroy`, a multi-line class declaration the earlier single-line `class \w+.*extends` grep pattern didn't match. Same treatment: composes a private `Subject<Action>`, exposes `next()` and `asObservable()`. Nothing in this repo currently subscribes to it directly — it's injected only to force eager DI instantiation in `store_module.ts`/`provide_store.ts` — but the class's entire reason to exist is to be observed externally (`@ngrx/effects`' `Actions` service wraps it once `effects` is added), so `asObservable()` was added now rather than left for a second pass later.

**Full-module audit results.** 191 occurrences of `extends` exist in `modules/store`; all but the classes above are either TypeScript generic constraints (`T extends Action`, hundreds of them, not runtime inheritance at all), interface-extends-interface (`RootStoreConfig extends StoreConfig`, `MemoizedSelector extends Selector` — interfaces have no implementation to leak, so ISP doesn't apply the same way), or the two cases already addressed above (`ReducerObservable`, and `ReducerManagerDispatcher extends ActionsSubject` — an abstract DI-token class extending this repo's own already-composed `ActionsSubject`, not an RxJS type, so there's no inherited operator surface to leak). `MockStore extends Store` is the one remaining concrete-class extension in the module — ordinary test-double subclassing of this repo's own `Store`, not RxJS inheritance, so it's unaffected by this decision.

### Why this is the right call, not just a different one

- **It's a real Interface Segregation Principle violation, not a style preference.** Every consumer of `Store` — every component, every effect, every test — depends on the entire RxJS Observable/Subject contract whether it uses it or not. ISP says clients shouldn't be forced to depend on interfaces they don't use; extending `Observable` for a `dispatch()`/`select()` API is exactly that.
- **The `lift()` override is direct evidence the fit was wrong.** A class that has to special-case its own base class's internal machinery just to keep its own subclass identity intact through a `.pipe()` call is fighting its own design, not benefiting from it.
- **Composition doesn't cost real functionality.** Every actual use in this codebase — dispatch, select, selectSignal, subscribe to the action bus, subscribe to the reducer stream — has an equally direct replacement (`state$`, `asObservable()`) that doesn't require inheriting from RxJS at all.
- **It's the kind of call a senior review would flag.** This is precisely the class of finding — "why does this class extend a library type it only partially needs" — that shows up in real architecture reviews of mature codebases, which is the point of redesigning it here rather than carrying it over unmodified like the rest of `store/src`.

### What it actually cost

- **`Store` losing the Observer interface is a real, deliberate behavior change**, not free. Two tests were deleted outright rather than adapted, because the capability they tested (`store.next()`/`store.error()` forwarding to the dispatcher, `result instanceof Store` after piping) no longer exists to test. Two more were trimmed to their still-valid half (`ActionsSubject`'s own "not completable" behavior, tested directly rather than through `Store`).
- **~40 call sites needed rewriting** across 6 spec files (`store.pipe(select(x))` → `store.select(x)`; `store.pipe(<other operator>)` → `store.state$.pipe(<operator>)`), split between the ergonomic method form and the standalone pipeable `select()` operator form (kept distinct on purpose — collapsing the "as operator" tests into `.select()` calls would have made them redundant with the adjacent "as property" tests instead of testing what they were written to test).
- **The build caught a ripple grep missed**: `MockStore`'s constructor already had its own private `state$: MockState<T>` field, which collided with `Store`'s new public `state$` once `MockStore extends Store` inherited it (TypeScript won't let a subclass narrow an inherited member's visibility). Renamed to `mockState$` — an internal-only name change, no public API impact on `MockStore` itself.
- **The second pass needed no test deletions**, unlike `Store`'s Observer-interface removal. `State`'s only externally-read Subject member was the synchronous `.value` getter (used by `integration.spec.ts`/`integration_signals.spec.ts`), which composition kept as an explicit getter rather than dropping. `mock_store.spec.ts` needed two call sites updated (`mockState.pipe(...)` → `mockState.state$.pipe(...)`, `stateObservable.pipe(...)` → `stateObservable.state$.pipe(...)`) once `MockState`/`StateObservable` stopped being directly pipeable.
- **`MockReducerManager` gained an `asObservable()` method it never had a caller for.** No test in the current suite invokes it — `REDUCER_MANAGER_PROVIDERS`' factory (the only real caller of `ReducerManager.asObservable()`) isn't part of `provideMockStore()`'s provider list. Added anyway: `provideMockStore` swaps `ReducerManager` for `MockReducerManager` via `useExisting`, and a mock that silently drops part of the real class's contract is a bug waiting for the day something starts calling it — the same reasoning behind adding `next()` to `MockState` for `MockStore.setState()` to call.
- **The third pass surfaced a real coverage gap, not just a missed class.** `ScannedActionsSubject` had no dedicated spec file — unlike `ActionsSubject`/`ReducerManager`, its own behavior was only ever exercised indirectly through `State`'s internal `next()` call, never asserted directly. `spec/scanned_actions_subject.spec.ts` was added alongside the fix, covering `next()` → `asObservable()` delivery and, deliberately, that a new subscriber does **not** see the last action — genuine `Subject` semantics that would silently have become `BehaviorSubject`-like (replaying) if the composition had used the wrong RxJS primitive.
- **A follow-up error-handling review of the five rewritten classes** (deliberately not the added source, which is battle-tested and checked out clean) found one real inconsistency between them: `ActionsSubject` got an `error()` method for API parity even though nothing in this repo calls it, but `ScannedActionsSubject` — the same shape of class, same reason to exist — didn't get the same treatment in the round-3 fix. Added, with a test confirming it forwards to `asObservable()` subscribers.

### Consequences going forward

`entity`, `effects`, `router-store`, `store-devtools`, and `data` — all still not yet added as of this writing — consume `Store`/`ActionsSubject`/`ReducerManager`/`State` directly. This redesign is finished, end to end, before adding any of them, specifically so each one targets the final shape once rather than needing a second pass. Anything in their source that relied on `Store extends Observable` or `State extends BehaviorSubject` (unlikely, but not yet verified) will surface as a build/test failure when each is added, the same way this redesign's own blast radius did — checked via the same discipline: grep first, verify with the real build/test/lint, fix what grep missed. That discipline is what caught `State`/`StateObservable` in the first place — a second `grep 'extends' modules/store` pass after the first round of fixes landed, not something planned upfront.

**This prediction came true the moment `effects` was added** — see the next section.

## Composition over inheritance, continued: `EffectSources` (`@ngrx/effects`)

**Status:** Done — [`cd346bd`](https://github.com/Terrence721/platform-main/commit/cd346bd).

Adding `effects` against this repo's already-composed `Store` surfaced real build/test failures immediately, exactly as predicted above:

- `effects_runner.ts` called `.subscribe(this.store)`, relying on `Store` implementing RxJS's `Observer<Action>` interface — removed in the `Store` redesign. Fixed to `.subscribe((action) => this.store.dispatch(action))`.
- `actions.ts`'s public `Actions` service injected `ScannedActionsSubject` directly and typed it as `Observable<V>`, which only worked because `ScannedActionsSubject` used to extend `Subject`. Fixed to call `.asObservable()` explicitly, guarded by `instanceof ScannedActionsSubject` so the testing package's `provideMockActions` (which constructs `Actions` directly with a plain `Observable`, bypassing DI entirely) still works with either shape.
- The real ngrx test suite calls `dispatcher.complete()` directly on an injected `ScannedActionsSubject`, expecting it to genuinely terminate the stream. This did **not** fit `ActionsSubject`'s pattern (whose `complete()` is an intentional no-op, so external code can't prematurely end the app's action bus) — checked against the real ngrx source before assuming that pattern applied here too, and confirmed `ScannedActionsSubject` never overrides `Subject.complete()` at all in the original. Added a real, working `complete()`.

Beyond adapting to `Store`'s already-finished redesign, the same composition-over-inheritance audit applied to `store` found a new instance of the same problem in `effects` itself: `EffectSources extends Subject<any>`, with its own domain methods (`addEffects()`) bolted onto the full inherited Subject surface, even though nothing external ever calls `.next()`/`.subscribe()`/`.pipe()` on an injected `EffectSources` — every consumer goes through `addEffects()`/`toActions()` only. Same fix as `store`'s classes: composes a private `Subject`, exposes `addEffects()`/`toActions()` as its actual contract.

`Actions extends Observable<V>` was deliberately left alone, for the same reason `ReducerObservable` was: its entire contract _is_ being pipeable — every consumer calls `.pipe()` on it, that's the whole point — with no unrelated method bolted on top. No ISP violation, nothing to fix.

Adapting `effect_sources.spec.ts` needed more than call-site renames: one test spied on `effectSources.next` directly (testing an implementation detail that's now a private field, removed since every test in the adjacent suite already covers `addEffects()` behaviorally), and the `toActions()` test helper rebound `this` to a synthetic marble-diagram Observable so the old `this.pipe(...)` worked directly — updated to wrap the synthetic source as `{ sources$: source, errorHandler, effectsErrorHandler }` to match the new internal shape.

## Schematics consolidation: one shared `modules/schematics`, not eight per-package copies

**Status:** Done — [`c10a528`](https://github.com/Terrence721/platform-main/commit/c10a528) adds `modules/schematics` itself, already containing every module's `ng-add` schematic (`store-ng-add`, `entity-ng-add`, `effects-ng-add`, `operators-ng-add`, `router-store-ng-add`, `store-devtools-ng-add`, `data-ng-add`, `component-store-ng-add`) alongside the module's own generator schematics (`action`, `container`, `store`, `effect`, ...). [`bd4d5be`](https://github.com/Terrence721/platform-main/commit/bd4d5be) removes the now-duplicated `schematics/` folder from each of the 8 source modules, plus the related `package.json`/`ng-package.json`/`tsconfig.schematics.json` cleanup. [`f78b930`](https://github.com/Terrence721/platform-main/commit/f78b930) and [`ebb4288`](https://github.com/Terrence721/platform-main/commit/ebb4288) fix two build/caching bugs the consolidation surfaced on CI — see the last bullet below.

### Context

Real ngrx/platform ships each module's `ng add @ngrx/<name>` schematic _inside that module's own package_ — `@ngrx/store` bundles its own `schematics/collection.json` with an `ng-add` entry, and so does `@ngrx/effects`, `@ngrx/data`, and every other installable package. That's not incidental: the Angular CLI's `ng add @ngrx/store` resolves the schematic from `@ngrx/store`'s own `package.json` `"schematics"` field. A schematic that lives somewhere else, under a different package name, is invisible to that resolution — `ng add` has no mechanism for "look in a sibling package instead."

Before this change, this repo mirrored that shape faithfully: all 8 already-added modules (`store`, `entity`, `effects`, `operators`, `router-store`, `store-devtools`, `data`, `component-store`) each carried its own `schematics/ng-add/` folder, its own `schematics/collection.json`, and its own `schematics/package.json` — 8 near-identical copies of the same `ng-add` plumbing, differing only in which module they wire up. This is the same duplication shape `schematics-core` was in before its own consolidation (phase 32) — 4 copies of the same AST/schematic utility code, merged into one shared `modules/schematics-core` on the grounds that the reason for the duplication (independent npm publishing) doesn't apply to a repo that never publishes any of these packages standalone.

### Decision

Applied the identical reasoning here, one level up: consolidate all 8 modules' `ng-add` schematics into the new `modules/schematics` package (the real `@ngrx/schematics` — the actual scaffolding generators like `ng generate @ngrx/schematics:action`, distinct from each module's own `ng-add` setup schematic), registered under module-qualified keys in its `collection.json` (`store-ng-add`, `entity-ng-add`, and so on — flat `ng-add` was already taken by `@ngrx/schematics`' own `ng-add` entry). Each of the 8 source modules' `schematics/` folder — collection, `ng-add/`, and their own `schematics/package.json` — is deleted outright rather than kept as a re-export shim; a shim would just be a second copy of the duplication problem with extra indirection.

**This deliberately breaks real `ng add @ngrx/store` (and the other 7) for an actual consumer of these packages**, because none of the 8 modules' own `package.json` files point at a `"schematics"` field anymore, and even if they did, the schematic implementation now lives in a different package (`@ngrx/schematics`) than the one CLI resolution would look in. Raised explicitly before doing this, not discovered after the fact: presented as a choice between (a) keep the per-module duplication, preserving real `ng add` fidelity, or (b) consolidate for DRY at the cost of that fidelity. Chosen deliberately: **(b), documented here** — this repo is `private: true` and never published, so no real `ng add @ngrx/store` invocation against these packages will ever happen from outside this workspace. The 8-way duplication was pure cost with no corresponding real-world benefit, the same judgment already applied to `schematics-core`.

### What it actually cost

- **8 sets of `SchematicTestRunner` test specs needed real changes, not renames.** Each module's `ng-add/index.spec.ts` constructed its `SchematicTestRunner` against that module's _own_ `dist/modules/<name>/schematics/collection.json` and called `runSchematic('ng-add', ...)`. Both had to change: the collection path now points at `dist/modules/schematics/collection.json`, and the schematic name at the module-qualified key (`'store-ng-add'`, `'data-ng-add'`, etc.) — the bare `'ng-add'` name is `@ngrx/schematics`' own entry, not any of these 8. `store`'s and `data`'s specs also each contain a genuinely unrelated `runSchematic`-adjacent reference (`RunSchematicTask('@ngrx/eslint-plugin', 'ng-add', {})`) that had to be left alone — same string, different schematic entirely.
- **A stale `dist/` artifact silently masked a real bug for a full verification pass.** The first full-suite run after the consolidation reported all 378 `schematics` tests passing — but that was against a leftover `dist/modules/store/schematics/collection.json` from before `store/schematics/` was deleted, not the new consolidated path. A subsequent rebuild (as part of an unrelated fix) cleared that stale file and immediately surfaced that all 8 moved spec files were still pointed at their old collection paths and schematic names. Re-verified afterward with `--skip-nx-cache` (Nx's local cache keys on input-file hashes, not on `dist/` presence, so a stale-artifact bug like this one doesn't force a cache miss on its own) to confirm the fix was real, not another illusion.
- **The ripple is otherwise mechanical, not architectural.** Every file that imports `'../../schematics-core'` — whether it lives at `modules/<name>/schematics/ng-add/index.ts` (the old location) or `modules/schematics/ng-add/<name>/index.ts` (the new one) — sits exactly 3 directories below `modules/`, so the relative import path itself needed zero changes. Only `collection.json` registration and the per-spec collection-path/schematic-name references moved.
- **The consolidation exposed a real, pre-existing fragility in how `schematics-core` gets built, once CI's remote cache was in the mix.** `schematics-core` never had a build target of its own — `dist/modules/schematics-core` only ever existed as an incidental side effect of whichever _consuming_ module's own `tsc` invocation happened to compile a file that imports it, and up to 8 different modules' `build` targets all separately declared that same output path as their own. That was tolerable when every module's compile ran on the same machine in the same pass; it stopped being tolerable the moment one of those tasks could be served from Nx's remote cache independently of the others — a stale cache restore for any one of them can silently overwrite a freshly-produced `schematics-core` with old content, and that's exactly what happened after the fix in `f78b930` landed: `schematics:build-package` was a genuine cache miss (the fix ran), but `schematics:build` — the target that actually needed `schematics-core` on disk — came back a remote cache hit from before the fix existed, undoing it. `ebb4288` gives `schematics-core` a real, independently-cacheable `build` target (reusing `tsconfig.lib.json`, a file that had sat unreferenced since the original `schematics-core` consolidation in phase 32) and removes the other 8 modules' redundant claim on that output, so exactly one task owns it. Caught only because the fix was verified against the actual failure shape — delete `dist/`, populate Nx's cache, delete `dist/` again, rebuild from cache — not just a fresh build, which had already been passing the whole time and gave no signal that anything was wrong.

### Consequences going forward

Any module added after this point (`signals`, `component`, `eslint-plugin`) that ships its own `ng-add` schematic gets it merged into `modules/schematics` the same way, registered as `<name>-ng-add`, rather than shipping a ninth per-module `schematics/` copy. The fidelity tradeoff this section documents applies to all of them equally — it's a repo-wide policy decision, not a one-off for the 8 modules that existed when it was made.
