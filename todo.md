### `Store` composition-over-inheritance redesign

**Why:** the real ngrx/platform `Store`/`ActionsSubject`/`ReducerManager` extend RxJS `Observable`/`BehaviorSubject`/`Subject` directly. That's a real Interface Segregation violation, not a style nitpick — it hands every consumer the entire RxJS operator surface (`pipe`, `lift`, `toPromise`, `forEach`, ...) when the actual contract is much narrower ("dispatch actions," "track the combined reducer"). `Store` even has to override `lift()` to keep RxJS's internal operator-chaining machinery from silently downgrading a `Store` back to a plain `Observable`. Composition — each class holds a private RxJS subject internally instead of extending one — closes that gap. Done one class at a time, in dependency order, each fully verified (tests/lint/build-package green) before moving to the next, since every module added afterward — `entity`, `effects`, `operators`, `router-store`, `store-devtools`, `data` so far — depends on these three classes' public shape.

Public surface deliberately hand-picked to match what an action bus actually needs (`next`, `subscribe`, `error`, `complete`, `asObservable`, `ngOnDestroy`) — no `pipe`/`lift`, not an `instanceof Observable`. Blast radius: one production call site (`state.ts`) + one test call site (`mock_store.spec.ts`) touched `ActionsSubject` as a raw Observable; both fixed. `store.spec.ts`'s direct `dispatcher.*` assertions needed no changes                                                                                                                                                                                                                                                                                                                                                                       |
