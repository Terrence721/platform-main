### `Store` composition-over-inheritance redesign

**Why:** the real ngrx/platform `Store`/`ActionsSubject`/`ReducerManager` extend RxJS `Observable`/`BehaviorSubject`/`Subject` directly. That's a real Interface Segregation violation, not a style nitpick — it hands every consumer the entire RxJS operator surface (`pipe`, `lift`, `toPromise`, `forEach`, ...) when the actual contract is much narrower ("dispatch actions," "track the combined reducer"). `Store` even has to override `lift()` just to keep RxJS's internal operator-chaining machinery from silently downgrading a `Store` back to a plain `Observable`. Composition — each class holds a private RxJS subject internally instead of extending one — closes that gap. Done one class at a time, in dependency order, each fully verified (tests/lint/build-package green) before moving to the next, since `entity`/`effects`/`router-store`/`store-devtools`/`data` all depend on these three classes' public shape once they're ported.

| Phase | Commit    | Date       | What                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| ----- | --------- | ---------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 16    | `99612ab` | 2026-08-06 | `ActionsSubject`: composition over inheritance. Public surface deliberately hand-picked to match what an action bus actually needs (`next`, `subscribe`, `error`, `complete`, `asObservable`, `ngOnDestroy`) — no `pipe`/`lift`, not an `instanceof Observable`. Blast radius: one production call site (`state.ts`) + one test call site (`mock_store.spec.ts`) touched `ActionsSubject` as a raw Observable; both fixed. `store.spec.ts`'s direct `dispatcher.*` assertions needed no changes                                                                                                                                                                                                     |
| 17    | `7c200db` | 2026-08-06 | `ReducerManager`: same redesign. Cleaner seam than `ActionsSubject` — a separate `ReducerObservable` DI token already existed for consumers that need the Observable view, so only the provider wiring (`useExisting` → a `useFactory` calling `.asObservable()`) and `ReducerManager`'s own internals changed. One blast-radius miss on the first pass: `integration.spec.ts` injected `ReducerManager` directly instead of the `ReducerObservable` token and called `.pipe()` on it — caught by the test run, fixed by switching the injection to match the codebase's own established pattern. `MockReducerManager` needed no changes (extends `BehaviorSubject` directly, not `ReducerManager`) |
